## 構成（要点）

- **講座情報は二重管理しない**：講座名・日時・内容・持ち物・教材・担当・対象学年・集団/個別・換算数は、ポータルの季節講習時間割（`seasonal_plans.published_body`）をそのまま読む。申込側で持つのは「定員・手動締切・料金倍率の確認値・教科の表示」だけ。
- **保護者画面** `/winter`（ログイン不要）：学年入力 → その学年の講座のみ（小学生/中学生/高校生が受講できる講座と明示）→ 期間・教科・種別で絞込 → 講座ごとに内容・全日時・担当・持ち物・教材・定価・残席 → 選択のたびに定価/講座数割引/きょうだい割引/合計（スマホは画面下に常時表示）→ 確認 → 送信 → 受付番号。
- **職員画面** `/portal/seasonal/applications`：受付期間・状態、講座ごとの定員・締切/再開・料金倍率・教科、申込一覧・取消・追加、CSV、操作履歴。権限 `seasonal_applications.view` / `.manage` を新設（校長に付与、他職員は個別付与）。
- **DB**（migration `20261021090000_seasonal_apply_capacity.sql`、**本番未適用**）：申込・定員・監査の表と、service_role 専用の DB 関数。申込・定員変更・締切・取消は講習単位のロックで1件ずつ処理し、ロック下で「公開・確定・対象学年・手動締切・定員・料金設定の版」を再確認する。
- **料金**（`lib/seasonal-apply-pricing.ts`）：画面と保存で同じ関数。保存額はサーバーで再計算し、ブラウザの金額は「表示額と一致するか」の照合にのみ使う。
  - 受講料 = P(学年, Σ換算数) ÷ Σ換算数 × Σ(換算数×料金倍率)、ドル未満四捨五入
  - 定価 = 1講座料金 × Σ(換算数×料金倍率)、講座数割引 = 定価 − 受講料
  - きょうだい割引：受講料の高い順に 0% / 20% / 30%（3人目以降）。割引額は1ドル未満切り捨て（＝PDFの表の「割引後は切り上げ」と一致）
  - 料金倍率（個別1.4・2コマ連続1.6）と換算数は別の値。時間・回数が標準と異なる講座は倍率を自動で決めず「要確認」→職員が入力するまで「準備中」。

## 検証結果

| 項目 | 方法 | 結果 |
| --- | --- | --- |
| 通常料金表・きょうだい割引表（MI Winter2025.pdf の1〜4講座の全値） | 単体テスト | 一致 |
| 混合受講（集団+個別1.4）、2コマ連続1.6、換算数と倍率の分離 | 単体・DB・画面 | 合格（例：小5 集団+個別=$216、高1 2コマ=$224） |
| サンクスギビング+冬期の合算／きょうだい間は合算しない | 単体・DB・画面 | 合格 |
| きょうだい2人（低い方20%）・3人（0/20/30%）、取消後の割引の移動 | 単体・DB・画面 | 合格（例：$224+$173=$397、取消後 $112+$224） |
| 対象学年のみ表示・学年区分の明示 | 画面（iPhone 13 幅） | 合格（小5で29講座、対象外なし） |
| 同じお子さんの日時重複 | 画面（選択不可＋理由）・サーバー | 合格 |
| 満席（定員変更→満席表示→保護者は選択不可、サーバーも拒否） | DB・画面 | 合格 |
| 手動締切（満席と別表示、残席あり）／再開 | DB・画面 | 合格 |
| 選択後に締切・満席→確認時に自動で外して案内／送信時に再確認して案内 | 画面・DB | 合格 |
| 締切日時を過ぎた後の送信 | DB | 拒否 |
| 同時申込（残り3席に20件同時） | 実PostgreSQL・別接続20本 | 成功ちょうど3件・保存3件 |
| 二重クリック／同じ操作IDで10回同時送信 | 実PostgreSQL・画面 | 申込1件・受付番号1つ |
| 保存後に応答が失われ、再送時には満席・受付終了 | DB | 保存済みの受付をそのまま返す |
| 表示額と保存額の不一致（表示後に職員が倍率変更） | DB | 保存せず「金額が変わりました」と案内 |
| 取消・追加で残席と料金が更新 | DB・画面・同時実行 | 合格（満席時の取消+申込の同時実行でも定員超過なし） |
| 権限（閲覧のみ／権限なし／保護者・匿名ロールからDB関数直呼び） | DB・画面 | 変更不可・閲覧不可・拒否 |
| 操作履歴（追記のみ、変更・削除不可） | DB | 合格 |
| ポータル既存テスト | `npm run test:all-lib`（2,966件）、`test:staff`、`test:ui`、`typecheck`、`lint`、`build`、`test:schema-contract-after-migrations`、`test:pending-migrations-isolated` | すべて合格 |

実行コマンド（ポータル）：
```
npm run test:seasonal-apply                 # 単体＋DB（PGlite）
npm run test:seasonal-apply-concurrency     # 実PostgreSQLの同時実行（TEST_PG_BIN、CIに追加済み）
SEASONAL_APPLY_DEMO=1 SEASONAL_APPLY_DEMO_SCENARIO=verification npm run dev   # 確認環境（Supabase設定なしの時だけ起動）
node scripts/e2e-seasonal-apply.mjs        # 画面確認（上の確認環境に対して）
```

検証中に見つけて直したもの（独立レビュー含む）：再送時に事前確認が先に走り保存済みの申込を「満席」と返す問題、表示額と保存額が食い違い得る問題、職員が同じ講座をきょうだい2人に同時追加すると席を二重に数える問題、別申込に分けると講座数割引・日程重複の判定をすり抜ける問題（→1家庭1申込に）、スマホでボタン文字が読めない・見出しの折り返しなどの表示崩れ、ポータル全体のCSSが干渉する問題。

## 未接続・未完了（要判断）

**本番には何も反映していません**（DB変更・公開・課金・メール送信なし。本番DBは講座データの読み取りのみ）。

1. **本番DBへの migration 適用・本番デプロイ**：未実施。適用・Renderへの手動デプロイは、内容をご確認いただいてからの作業です。手順：migration 適用 → `npm run refresh:contract` → ブランチをpush・PR → Renderで `Deploy latest commit` → `/api/ready` 確認。
2. **講座の確定（ポータル側の入力）**：68講座のうち確定は9講座。残り59講座は時間割で「集団/個別・換算数・根拠・確定」の入力が必要（それまで保護者画面では「準備中」）。
3. **料金の扱いを決めていただく講座**（勝手に決めていません）
   - 2コマ連続（14:00-17:00×3回）：「版画で年賀状を作ろう」（冬期1）、「版画で年賀状」（冬期3）→ 倍率は1.6自動、**換算数（何講座と数えるか）は未定**
   - 1回のみ：マンスリー対策 小3算数、クリスマスカード作り、オーナメント作り、マンスリー対策 中学生英語、マンスリー対策 小2（いずれも冬期1）→ 倍率・換算数とも要入力
   - 2回のみ：中学個別×2（サンクスギビング）→ 同上
4. **保護者向け公開ゲート**：既存の季節講習には DB 管理者だけが開けるゲート（`publication_enabled`、現在 false）があり、本機能もこれが開いて講座が「公開」されるまで受け付けません。
5. **既存のログイン型申込（`/guardian/seasonal`）との併用**：両方を開くと席を別々に数えます。冬期は本機能（学年入力の公開フォーム）に一本化することを推奨します。
6. **請求処理への連携**：未接続。申込額はCSVで受け渡し。既存の季節講習請求（`seasonal_invoices`）はログイン型申込の選択を元にしているため、どちらを正本にするか決める必要があります（請求エンジンは高リスク領域のため今回は触れていません）。
7. **受付メール**：未実装（送信していないものを送信済みとは表示しません）。保護者には受付番号の画面を控えるよう案内。
8. **荒らし対策**：ボット除け（見えない入力欄）と1家庭1申込のみ。架空のメールで席を埋めることへの対策（回数制限・確認メール等）は未実装。
9. **申込締切日・問い合わせ先・公開URL**：案内文に記入欄を残しています（昨年度の日付は転用していません）。
10. **会社ロゴ**：添付が届かなかったため、ポータルの請求書等で使用中の正式ロゴ（`public/sundai-logo.png`）を使用。校章は添付画像を縮小のみ（描き直しなし）。
11. **夏の申込ページ・スプレッドシート**：この作業環境からは接続できませんでした（ネットワーク制限）。仕組みは `sundai-summer-library` のソース（定員の初期値12、申込一覧からの申込数・残席の再計算、スクリプトロック）で確認しました。夏のシートは変更していません。
12. **端数の差**：きょうだい割引で5講座以上のとき、PDFの「1講座ごと」の割引額を足す方式と比べ、合計で$1違う場合があります（本機能は合計に対して1回だけ端数処理）。
13. **幼稚園**：ポータルに幼稚園の講座がないため、学年は小1〜高3のみ。
14. **担当表示**：ポータルの講師マスターの名前を表示します（例：ラベル「ドーナー」の講座は「ゆい先生」）。表記の確認をお願いします。
15. **確認環境の制約**：ブラウザの中だけで動くため、同時申込の再現・CSVの保存・印刷はできません（再読み込みで初期状態に戻ります）。同時実行は上記の実PostgreSQLテストで確認済み。確認環境の公開先でのWebAssembly動作は、こちらから実機確認できていません（起動できない場合は画面にエラーが出ます）。
