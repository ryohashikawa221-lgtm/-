# 比較監査プロンプト（ChatGPT 用）

## 使い方
1. 下の「プロンプト本文」をそのまま ChatGPT に貼る。
2. 次のファイルを添付する（どちらの案かは伏せて「案A」「案B」とファイル名を付け替える）。
   - 依頼文（今回 Claude と Codex に渡した原文）
   - `MI Winter2025.pdf`
   - 各案の実装ソース（Claude案は `portal-patch/0001-winter-apply-2026.patch`）
   - 各案の報告書・案内文・職員手順・画面写真（Claude案は `README.md`、`01_保護者向け案内文.md`、`02_職員向け手順.md`、`screenshots/`）
   - 各案の確認環境URL（あれば）
3. 片方の資料が足りない項目は「資料なし」と書いて渡す（推測で補わせない）。

## プロンプト本文

あなたは、日本人保護者向けの学習塾の申込システムを審査する、独立した上級監査人です。
同じ依頼に対して2つのチームが作った「案A」と「案B」を比較し、**本番に採用すべき方**を判定してください。
どちらがどのAIで作られたかは考慮しないでください。添付資料に書かれていること・ソースから確認できることだけで判断し、確認できないことは「未確認」と書いてください。推測で加点・減点しないでください。

### 背景
- 駿台ミシガン国際学院（米国ミシガン州）の 2026年度 サンクスギビング・冬期講習。
- 既存システム：Next.js（App Router）＋ Supabase（PostgreSQL）の職員・保護者ポータル。本番は Render。講座情報はポータルの季節講習時間割に保存されている。
- 依頼文（添付）が唯一の要件です。依頼文にない機能を作ったことは加点しません。依頼文に反する点は減点します。

### 手順
1. 依頼文を読み、**要件チェックリスト**を作ってください（最低でも下の「必須要件」を含める）。
2. 案A・案Bそれぞれについて、各要件を「満たす／一部／満たさない／未確認」で判定し、**根拠（ファイル名と行・関数名、または資料の該当箇所）**を1行で書いてください。
3. 下の「重点監査」を、ソースを読んで確認してください。不具合を見つけたら、**再現手順（具体的な入力と結果）**を書いてください。再現手順を書けないものは「懸念」として分けてください。
4. 採点表で点数を付け、総合判定を出してください。

### 必須要件（抜けがないか確認）
- 講座情報はポータルの最新データを使い、二重編集にならない（昨年度PDFの講座・日付を転用していない）
- 最初に学年を入力 → その学年の講座だけ表示 → 小学生／中学生／高校生の区分が明確
- 期間・教科・講座種別で絞り込める／各講座で内容・全日時・担当・持ち物・教材・料金・残席が見られる
- 選択・解除のたびに 定価・講座数割引・きょうだい割引・支払合計 を表示、スマホでも常に金額が分かる
- きょうだい一括申込（学年・講座・料金はお子さんごと）
- 同じお子さんの日時重複を防ぐ
- 確認→送信→保存成功後に受付番号と内容を表示（仮選択を完了扱いしない）
- 定員初期値 集団12・個別3、講座ごとに変更可
- 講座ごとの手動締切・再開。**手動締切と満席を別状態**で管理・表示
- 受付中／満席／締切／準備中が保護者に分かる
- 締切・満席は**サーバー側でも拒否**、選択後に状態が変わったら送信時に再確認して案内
- **同時申込でも定員超過しない**／取消・変更で残席が正しく戻る
- 定員・受付状態を変更できる**権限管理**／**変更履歴**
- 残席は実データから算出
- 料金：通常料金表（1講座 小$100・中$120・高$140 …、5講座以降 +$60/$72/$84）、個別1.4倍、2コマ連続1.6倍（1.8倍は不可）、サンクスギビング＋冬期は同じお子さんで合算、きょうだい間は合算しない、2人＝低い方20%引、3人＝高い順に0/20/30%
- 料金倍率と「講座数割引の換算数」を別の設定にし、標準外の講座の扱いを勝手に決めず確認項目にしている
- 料金はサーバーで再計算し、ブラウザの金額を信用しない／端数処理が明確で、表示・保存・請求の金額が一致
- 夏の料金・割引を流用していない
- 表記「お子さん」で統一（「お子様」「お子さま」なし）／正式ロゴと校章を描き直さずに使用／保護者画面に開発者向け説明が混ざっていない
- 二重クリック・通信再試行で重複申込にならない
- 受付メールを実装した場合、未送信を送信済みと表示しない
- 既存の生徒情報・夏の申込・通常授業・請求処理を壊していない／本番の公開・課金・メール送信を無断で行っていない
- ホスティングは Render
- 納品物：確認環境、ソース、保護者向け案内文、職員向け手順、検証結果と未完了項目の明示

### 重点監査（ソースで確認する）
1. **同時実行**：2人が最後の1席に同時に送信したとき、どこで直列化されるか（行ロック・アドバイザリロック・制約など）。ロックの順序が処理ごとに一致しているか。デッドロックの可能性。
2. **締切と満席**：画面で「受付中」の講座を選んだ後に締切・満席になった場合、サーバーが拒否し、保存が一部だけ残らないか。
3. **二重送信**：同じ送信を2回送ったとき、保存後に応答が失われて再送したとき、申込が1件のままで同じ受付番号が返るか。
4. **料金**：手計算で次を確かめる。
   - 小5：集団1講座＋個別1講座 → $216
   - 高1：2コマ連続（集団）1講座のみ → $224
   - 上の2人がきょうだい → 合計 $397（低い方 $216 を20%引 → $173）
   - 3人：高2が2講座 $252、中1が1講座 $120、小4が1講座 $100 → $252＋$96＋$70＝$418
   - 中学生2講座 $216 の20%引 → $173、高校生2講座 $252 の30%引 → $177（PDFの表と一致するか）
   - 取消で受講料の順位が入れ替わったとき、きょうだい割引が正しく付け替わるか
5. **金額の信頼性**：ブラウザから送られた金額を保存に使っていないか。表示額と保存額が食い違う場合（表示後に職員が料金設定を変えた等）の扱い。
6. **権限**：保護者・匿名ユーザー・閲覧のみの職員が、定員変更・締切・取消を実行できないか（画面だけでなくサーバー／DB側でも）。
7. **既存システムへの影響**：既存のテーブル・請求エンジン・通常授業・夏の申込に書き込んでいないか。migration が本番に未適用のまま安全に段階導入できるか。確認用のモードが本番で誤って有効にならないか。
8. **運用**：講座情報の正本が1つか。定員・締切を職員が画面から変えられるか（ハードコードしていないか）。
9. **保護者の使いやすさ**：スマホ幅で、学年入力から送信まで迷わず進めるか（画面写真で判断）。エラー時に何をすればよいか分かるか。

### 採点表（100点）
| 観点 | 配点 |
| --- | ---: |
| 要件の充足（必須要件） | 25 |
| 定員・締切・同時実行・二重送信の正しさ | 20 |
| 料金計算の正しさと金額の一貫性 | 15 |
| 権限・履歴・既存システムの保護（安全性） | 15 |
| 保護者・職員の使いやすさ（スマホ含む） | 10 |
| 検証の実在性（テストが実際に要件を確かめているか、結果が再現可能か） | 10 |
| 報告の正直さ（未完了・未確認を正しく区別しているか） | 5 |

### 出力形式
1. **結論**（最初に1〜3行）：採用すべき案と、決め手。
2. **採点表**：案A・案Bの観点別の点数と合計。
3. **要件チェックリスト**：表（要件／案A／案B／根拠）。
4. **確認できた不具合**：案ごとに、重大度（高・中・低）、該当箇所、再現手順、影響。
5. **懸念（再現手順なし）**：案ごとに箇条書き。
6. **もう一方から取り入れるべき点**：採用しない案の良い部分で、採用案に移すべきもの。
7. **本番導入前に必ず直すこと**：採用案について、優先順に。
8. **未確認事項**：資料が足りず判断できなかったこと。

注意：秘密情報や個人情報（生徒・保護者の氏名、メールなど）が資料に含まれていても、出力には書かないでください。
